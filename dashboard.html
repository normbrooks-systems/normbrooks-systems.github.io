Case study 01

Production Dashboard

From a two-week dashboard to a lightweight production-management system

In January 2025, I was asked to build a production dashboard for one department at a high-volume direct-mail company. The immediate need was straightforward: operators and supervisors needed a faster way to see whether production was on pace, where time was being lost, and whether a weak number represented a bad interval or a broader pattern.

I built the first version in Google Sheets in about two weeks.

That solved the first problem and exposed the next one almost immediately. Other departments wanted the same visibility, but their operations were not identical. Machine lists changed. Operator counts changed. Shift structures changed. Targets changed. Even the meaning of a good production interval varied by department.

A dashboard that had to be rebuilt every time would not scale. The project became less about a single screen and more about separating the visible interface from the operating assumptions underneath it.

The system underneath the screen

The visible dashboard was intentionally simple. Operators needed to be able to glance at a floor display and understand where they stood. Supervisors needed current production, pace against goal, and enough recent history to recognize when something had changed.

Underneath that display, the workbook became a layered operational system.

Daily shift sheets combined production inputs with calculated setup and downtime, working hours, actual pieces per hour, labor cost per piece, checkpoint performance, pace, and projected final output. A separate control layer held information that should not be hard-coded into the display: operator rosters, machine assignments, goals, shift parameters, and references to the active production sheets.

The dashboard layer then resolved the current operating state from those structures rather than embedding names, machines, dates, and goals directly into dozens of display formulas.

A separate operator-production view supported longer-term analysis by operator or machine over a selectable date range. It could summarize production percentage, hours, average performance, and uptime/downtime relationships while charting the selected history.

A reconstructed example of the workbook contains 14 sheets and more than 30,000 formula cells. That number is not the point by itself. The important part was that the complexity was divided into layers with different jobs instead of being scattered through the user interface.

Configuration instead of reconstruction

The first version taught me what made the system difficult to maintain. If an operator name, goal, shift boundary, or machine assignment is embedded directly into the formula that displays it, every change becomes a search-and-repair exercise.

I moved those variables into control structures and made the display resolve them from configuration.

That changed redeployment from a formula-writing problem into a configuration problem. A department could have a different roster, machine set, goals, or shift structure without requiring the visible dashboard to be redesigned around those differences.

The same basic architecture ultimately supported multiple deployments across facilities in Virginia and Iowa. The presentation could remain familiar while the operating model underneath it changed to match each department.

That separation is the part of the project I value most. The dashboard did not become useful because it had complicated formulas. It became useful because the complexity was increasingly kept away from the people who only needed the result.

Planning the shift before measuring it

As the system matured, I began building tools around the reporting layer rather than simply adding more information to the dashboard.

One of those tools was the Planner: a printable shift-planning sheet that let a supervisor assign operators to machines, reconfigure those assignments as staffing changed, and capture call-outs at a glance. It was designed around the existing two-hour capture window, so the same sheet could remain useful as a working document while the shift was being established.

The Planner was not a separate dead-end document. Once the assignments were settled, a transfer function wrote the selected operator and machine assignments into the initial values of the appropriate daily production sheets.

That meant the shift could be planned once and then used to initialize the reporting system instead of requiring the same assignments to be entered independently in multiple places.

In December 2025, I traveled to the company's Iowa facility to help configure the Planner and related support sheets for that operation. By that point, the work had moved beyond a single departmental dashboard and into cross-facility production tooling.

Designing for the people using it

The visual layer mattered just as much as the calculations.

The dashboard used performance bands that could be understood from floor distance. Operations originally wanted three colors. I expanded the scheme to five: red for serious underperformance, yellow as a transition band, green for solid performance, blue around target, and purple for unusually strong performance.

When I supervised the night shift, I called the purple band Royalty.

That was not a statistical innovation. It was a human one. A dashboard that only highlights failure trains people to look for failure. Giving exceptional performance its own visible state gave operators something positive to chase as well.

The dashboard also showed recent history beside current performance. That made a low number more useful: a supervisor could see whether an operator was consistently struggling or whether today's result was unusual enough to investigate. The same principle applied to pace and projections. The goal was not to display every number we could calculate. It was to make deviations visible early enough to do something about them.

What the dashboard did — and did not — cause

During my time supervising the night shift, average production rose and ultimately held at roughly 20% above the baseline I inherited.

I do not attribute that result to a spreadsheet.

Staffing decisions, scheduling, expectations, coaching, and day-to-day leadership all mattered. The dashboard's contribution was visibility. Operators could see their latest recorded production. Supervisors could see which machines were falling behind before the shift was over. Much of the data was entered manually, so the reporting reflected the latest entries rather than continuous automated capture. Historical comparisons made it easier to distinguish a recurring problem from a one-off event.

The spreadsheet was the floor under the number. It was not the engine.

That distinction matters because operational tools are easy to oversell. A dashboard cannot manage a department. It can make the state of the department harder to misunderstand.

Approaching MES-like functionality

By late 2025, calling the project only a dashboard no longer described its full scope.

The system could support shift planning, attendance/call-out visibility, machine and operator assignments, initialization of daily production records, production capture, setup and downtime tracking, pace and projections, historical operator and machine analysis, and floor reporting based on the latest entered data. In the version I developed for my own supervisory use, I also automated portions of recurring forms and employee-related administrative work.

It was not a formal Manufacturing Execution System (MES), and I do not present it as one. But its direction was increasingly MES-adjacent: plan the work, initialize the shift, capture what happened, make the current state visible, preserve history, and reduce repetitive administrative steps around the process.

Where I was taking it next

The remaining limitation was that much of the production data still depended on people entering it.

I built a Raspberry Pi 4-based production-counter prototype and continued developing a machine-side concept that could combine automated counts with operator and job information. The intent was to collect production information closer to the machine, preserve it in the Sheets-based operating layer, and ultimately make that information available to existing enterprise workflows without requiring every production event to begin at a shared workstation.

I was also simplifying parts of the original spreadsheet architecture as I went. The first dashboard had relied heavily on indirect references and other formula techniques because Sheets was the tool available and the system had grown quickly. Later development moved toward fewer, cleaner lookup paths and more automated data collection.

Development continued into my final weeks with the company, but the automated capture and integration work did not reach production deployment. I present those pieces as development work rather than finished implementations.

What this project represents

The project started as a request for a screen.

What it became was a configurable production-management system built inside tools the organization already used. It combined planning, production calculations, configuration, current-state reporting, historical analysis, administrative automation, and a visual language designed for the people actually doing the work.

The implementation matters, but the broader lesson has followed me into other projects: the best system is not the one with the most sophisticated architecture on paper. It is the one that captures the right information, makes the important state obvious, reduces unnecessary human work, and can survive the next change without forcing everyone to start over.
